Grid geometry (measured by existence probes on the sorted TSV):

- Coordinates are signed decimal in filenames: `{X}` ∈ [−8 .. 43], `{Y}` ∈
  [0 .. 39]. No `x-9`, no `x≤−10`, no negative `y`, no `y≥40` anywhere.
- Coverage is **ragged, not rectangular**: albedo bbox enumerates 52×40 = 2,080
  possible cells but only 1,377 exist (≥703 absent = off-world/ocean). Columns
  are partial (e.g. `x=-1` holds only y 8–23; `x40–x43` only y 28–31 — a far-east
  island block). Lexicographic filename order ≠ numeric order; the classifier
  MUST parse ints (`-8` sorts before `-2` numerically, after it lexically).
- The four full-res classes and the `_s` pyramid share **one identical cell
  set**: all five classes cover exactly the same 1,377 cells (set diff zero in
  both directions, probed 2026-08-25). Full ↔ `_s` co-presence is 100%, so the
  D7 ratio test runs on every cell with no sampling caveat. Per-class cell-set
  identity stays a cheap test assertion (**D3** emits the shared hole map once).
- Placeholders/duplicates, honestly — three repeated payloads exist and are
  kept and catalogued, never dropped (realtime-goal: captures are target data):

  | class | crc32-family | n tiles | repeated bytes |
  |---|---|---:|---:|
  | albedo | `0ff430e9` | 276 | 72,387,072 (~69 MiB) — flat/ocean texture; tail ys 33–39 of complete columns plus mid-column spread incl. `x30` |
  | splat | `78c858d4` | 273 | 4,580,214,912 (~4.27 GiB) — likely a uniform "no-splat" ground mask over ocean/off-world cells |
  | splat / height | `782458d4` / `db05e56a` | 2 + 2 | incidental pairs |

  splat-mask cells are a **strict subset** of the 276 `0ff430e9`

  "uniform no-splat over ocean" predicts. Full interpretation (are these ocean

## 2. Format handling

**DDS variants — measured; the ambiguity table is retired.** Headers were read
this pass straight off extracted tiles (two per class, identical), and every
payload arithmetic closes:

| class | payload B | measured header | arithmetic |
|---|---:|---|---|
| albedo | 262,144 | 512×512 FourCC `DXT5` (BC3), mip-less | 512² × 1 B/px = 262,144 ✓ |
| normal | 2,097,152 | 2048×2048 FourCC `DXT1` (BC1), mip-less | 2048² × 0.5 B/px = 2,097,152 ✓ |
| splat | 16,777,216 | 2048×2048 uncompressed RGBA8 (flags 0x41 = DDPF_ALPHAPIXELS+DDPF_RGB, RGBBitCount 32), mip-less | 2048² × 4 B/px = 16,777,216 ✓ |

All three carry the classic 128-byte header only — no DX10 extended header,
which is also why albedo was never BC7 (that format requires the +20-byte DX10
header). The earlier draft's "consistent readings" column is retired outright:
two of its branches were arithmetically impossible (1024² block-compressed is
half the normal payload; 4096² BC1 is half the splat payload).

Note the ordering anomaly stands: normal/splat out-resolve albedo per cell.
**D1** narrows to a uniformity sweep: every one of the 4,131 files gets a
recorded (format, dims, mips) matching its class triple above — outliers
listed, never silently dropped, **zero unexplained payloads**. Extraction
itself is already proven (TOOL §1: 6,886/6,886 adler-MATCH, 1,612 entries >4
GiB sampled OK).

**`.raw` layout hypothesis + verification.** Working hypothesis: headerless
float32 scalar height grids — full = 512²×f32 = 1,048,576 B, `_s` = 128²×f32 =
65,536 B (TOOL §3's peek called them "float coordinate pairs"; either way they
carry **no container magic**). Two consequences:

1. Magic-routing does not apply to `.raw`: classify by path pattern + size.
   The harvest run's detect step mislabelled **16 raw tiles** (8 full + 8
   `_s`) — 6 as json, 10 as xml — because their first float byte coincides
   with `{`/`<`; the real `textures.json` sits inside the same json count, so
   `map.summary.json` reads `json` 7 (= those 6 + textures.json) + `xml` 10.
   Recorded here as a known false-positive mode so nobody re-derives "hidden
   JSONs in map.pak". The sole real JSON is `textures.json`.
2. Proof steps (**D2**): reinterpret as f32 grids → value-range stats must be
   plausible elevations (finite, bounded); adjacent-tile edge-continuity metric
   (mean abs Δ across shared edges) must sit well inside the global gradient;
   the 4 MiB `height_x0_y0.raw` outlier gets its own explanation (1024²?
   double layer? higher LOD at world origin) written into EXTRACTION-LOG.

**Mosaic assembly order.** Tiles address a global raster: `origin_px(x,y) =
(x·W_layer, y·H_layer)` with W/H from D1 per layer. Assembly = numeric sort by
(x,y), alpha-composite absent cells as transparent (never fabricate ocean from
the placeholder texture — ship both: real placeholder pixels stay where the
pack puts them; absent cells stay empty). Y-axis direction (north-up vs
south-up) is not yet provable → resolved in **D6** by comparing an assembled
low-zoom overview against INDEX `shot-05` (strategic map) coastline/region
positions; the chosen orientation is recorded in maps.json, never hardcoded in
components.

## 4. `maps.json` registry schema

Emitted to `extracted/` (consumed through F2 contracts; frontend never reads
pak state). One registry, layered:

```jsonc
{
  "buildid": 20318128,
  // The sample deliberately carries null/<D6>/<D1> placeholders: answers D6
  // exists to produce are never pre-pinned here (a CodeWriter copying the
  // sample must not inherit assumptions). Pinned form once the digs land,
  // kept in comment only: yAxis "north-up", transform d -1, tileSizePx 512,
  // format "webp".
  "crs": { "type": "wartales-world",
           "yAxis": null,                 // pinned by D6 ("north-up"|"south-up"), never assumed
           "transform": { "a": 1, "b": 0, "c": 0, "d": "<D6>",
                          "tileUnitPx": "<D1 per layer>" } },
  "layers": [
    { "id": "world-strategic", "kind": "tiles",
      "imagery": { "tileTemplate": "/map-tiles/albedo/{x}/{y}.webp",
                   "tileSizePx": null,   // pinned by the D1/export decision, not assumed (source measures 512²)
                   "format": null,       // pinned with the tile-export step
                   "minZoom": 0, "maxZoom": 3 },
      "bounds": { "xMin": -8, "yMin": 0, "xMax": 43, "yMax": 39 },
      "cells": "cells/albedo.cells.json",
      "provenance": "client-extracted", "source": "map.pak:data/albedo" },
    { "id": "region-overlays", "kind": "vector",
      "sourceRef": "res.pak:/content/worldmap.l3d",
      "bounds": "<from decoded scene, D5>" }
    // + height, marker-layers, hunt-regions, fief-districts;
    // battle-tactical registered separately (own crs.type) when P1 opens.
  ],
  "regions": [ { "id": "<CDB region row id>", "nameKey": "<EXP key>",
                 "polygonRef": "<D5 output|null>", "bounds": "<measured>" } ]
}
```

Rules: every numeric field traceable to a dig artifact; `null` beats guesses
(absence is data); regenerate per rerun; schema published in `contracts/`.

Registry scope (FRAMEWORK §2.6 names dungeons/instances explicitly): Wartales
has **no dungeon/instance map family** — interiors are scene backgrounds (PRE
`/backgrounds/*` are scenes, not mappable spaces) and battles belong to the
separate battle-tactical CRS above, which is the only non-world CRS. Recorded
here as a measured negative so no builder or arbiter has to re-ask it.

**Storage & publication planes** ([DR-2026-08-18-media-scope]). The served
plane carries **only albedo-derived webp tiles** (`/map-tiles/**` → site
public dir or CDN at site-build time; never git — game-data-in-git ban). Splat
(23.1 GB), normal (2.89 GB) and the `.raw` classes (height 1.45 GB + `_s`
pyramid 90 MB = 1.54 GB) stay data-plane inputs under `extracted/` — textbook
catalogue/offload candidates handed to `MEDIA-CATALOGUE` at harvest close, so
no ~27 GB deploy happens by default and no offload decision is made by
silence.
