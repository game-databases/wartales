## Verification method

No ruling rests on a reviewer's prose. Every load-bearing claim was
re-derived on this machine against the scratch TSVs and the live paks
(`A:\SteamLibrary\steamapps\common\Wartales\`, read-only) with an
**independent second parser** (not `wtpak.py`) implementing the R2 format
model:

- Tree starts at byte **0x0C**, not 0x10 — zero-slack parse of all four
  paks, file counts 936 / 17,131 / 15,248 / 6,886, `"DATA"` marker at
  `[header_size−4..header_size)` on all four.
- map.pak global position tiling `[0, 27,888,786,275)` — no gap, no
  overlap, mixed flags; first flag-2 entry sits at exactly **2,148,002,816**
  = Σ(flag-0 sizes); `/assets/worldmap/data/normal/normal_x10_y14.dds`
  recomputed adler32 == stored == TSV col 5 at that computed position.
- Live headers: version byte **0** ×4; i32@0x08 =
  767,068,478 / +626,799,415 / −1,223,561,650 / +2,118,982,499 (res /
  assets / content / map) — i.e. Σsizes reduced mod 2³², signed.
- map.pak on disk measures **27,889,015,798 B** = Σsizes + header_size
  (229,523) exactly.
- The 17 `/lang/*` entries were extracted and adler-verified **for the
  first time ever**: 17/17 MATCH vs stored and vs TSV (see F1).
- TSVs: CRLF row endings ×4; map.pak flag-2 offset column steps by exactly
  2²⁸ across its first rows and its max(offset+size) = 4,278,190,208 <
  data span 27.9e9 — self-impossible, synthetic.
- Recounts: `.fbx` = 6,946 (assets, 2,091,136,833 B) + 258 (content,
  34,642,946 B) = **7,204 / 2,125,779,779 B ≈ 2.13 GB** pack-wide;
  `/content/regions/` = POI 453 / Towns 156 / **Secret 12** / **Secrets
  103** = 724; map.pak `.json` = exactly one
  (`/assets/worldmap/data/textures.json`, 2,531 B, flag-2), `.dds` 4,131,
  `.raw` 2,754.

## Arbiter-added findings

- **A1 (spec-harvest §2.2, MINOR but normative — ride in the same edit):**
  the byte-layout block contradicts the seed reader it normatively binds.
  It claims "Header (16 B)" with the index blob at "[16 .. header_size−4)",
  but `wtpak.read_header` consumes **12** bytes (magic 3 + version 1 +
  two i32) and the DFS tree begins immediately at **0x0C** — the index
  blob is "[12 .. header_size−4)". recon §2 already said "from 0x0C".
  Proven independently: tree-start 12 gives zero slack and exact counts on
  all four paks; tree-start 16 fails (slack 229,421 on map.pak). A
  TestWriter mini-pak writer mirroring §2.2 literally would emit 4 alien
  bytes that `wtpak.Reader` cannot parse — caught loudly, but only after a
  wasted cycle and a temptation to fork the reader that §1 forbids. Fix:
  correct the two boundary lines; add a unit assertion that the synthetic
  writer's output round-trips through `wtpak.Reader`.
- **A2 (spec.md missing-data, MINOR — ride in the same edit):** two rows
  are now resolved by the harvest contract and go stale if untouched:
  "flag-2 file-node fields (A,B) unresolved" (resolved: bit-2 selects f64
  position encoding) and "pak header u32@0x08 unresolved" (resolved: i32
  dataSize, Σsizes mod 2³²). Restate as resolved-by-[`spec-harvest.mdx`](./spec-harvest.mdx)
  §2.1 pending CodeWriter proof, and backfill the version byte (0) into
  the EXTRACTION-LOG plan.
- No further holes found on the brief's hunt list: rule-8 discipline holds
  (every open question — world↔tile transform, HBSON decode, difficulty
  parameter sets, achievement conditions, recipe/class containers — is a
  dataminer P0/P1; pieces.mdx marks frontend data-deps as consumers);
  D2 provenance classes respected (coverage labels present, license facts
