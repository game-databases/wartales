# Decompile dig 1 — the hlboot.dat structure is fully recovered

Follow-up to [toolchain-validation §2](toolchain-validation.mdx): the
HashLink bytecode layer of Wartales (client buildid 20318128) is now parsed
end-to-end with a **zero-slack round-trip proof** and an **independent
two-implementation cross-check**. Artifacts:
[`extracted/logic/hl-structure/`](../extracted/logic/hl-structure/WALK-PROOF.mdx)
(7 datasets + proof), tool: `pipeline/tools/hlboot_probe.py --emit`.

## 1. What the fork actually adds — R2 verdicts corrected

The R2 scout's working theory ("type-kinds ≥19 exist that no public table
names; observed kinds 22–31+") was an artifact of its own desync: the seed
probe rewound past the canonical debug-files block (which sits at
`0x22E65B–0x238AA9`, strictly NUL-validated, ndf=1,609) and read blob bytes
as type-kind ids. The completed walk proves:

1. **Type kinds: NO fork extensions occur.** All 46,891 types use the
   public enum family carried by the shipped `libhl.dll` (`hlt_dynobj`,
   `hl_guid_str` exports ⇒ HDYN=9…HPACKED=22, HGUID=23 — exactly
   [`_refs/hl.h`](../pipeline/tools/_refs/hl.h)). Full per-kind histogram in
   [WALK-PROOF](../extracted/logic/hl-structure/WALK-PROOF.mdx).
   Why [hlbc](https://github.com/Gui-Yom/hlbc) still dies on kind '22':
   its release tables end below this build's numbering — a tool gap, not a
   bytecode fork.
2. **Opcode table: public v4 table + 3 known fork-family additions.** Only
   ids 0–98 occur in this build; the Shiro/DeadCells fork family's extras
   `Prefetch(reg,field,int)`, `Asm(int,int,reg)`, `Catch(reg)` (ids 99–101,
   per crashlink) are pinned in our tool for future builds.
3. **Fork deviations that ARE real** (all handled):
   - function storage order is not findex order;
   - findex space is sparse over the combined functions+natives span
     (0..52,682; entrypoint f#52,548 = exact function match — resolves §2's
     "entrypoint > nfunctions" flag);
   - assigns are `(stringRef, int)` pairs (debugger variable tracking), not
     reg/type pairs;
   - native lib names appear with a literal `?` prefix variant
     (`?steam`, `?hlgog`, `?hlwwise`, `?std`, `?directx`, `?ui`) alongside
     hard forms — consistent with soft/optional native binding in the
     loader.
4. **Section layout is canonical** after all: strings → debug-files block →
   types → globals → natives → functions(+debug+assigns) → constants → EOF.

## 3. Next step — full decompiler

Everything a decompiler needs is now tabular and verified; the remaining
work is codegen, not discovery:

1. **Operand-level disassembler** (`hl_disasm.py`): decode
   `opcodes.jsonl.gz` against the pinned opcode semantics into typed IR
   (per-opcode operand roles: reg/ref-global/ref-string/jump-offset…).
   Jump targets resolve within each function's op range — cheap CFG build.
2. **CFG + structured text**: dominator tree per function, if/while/switch
   reconstruction (OSwitch payloads already parsed), expression folding over
   register SSA-ish chains. Target output:
   `extracted/decompiled/hl/{module-path}.hx` mirrors of the 1,609 debug
   source paths, so every game mechanic lands next to its original file
   name (extraction doctrine: raw decompile is a first-class output).
3. **Name recovery**: method names come from owner-class protos
   (obj.protos findex→function), closures from debug paths (`fun$init`
   pattern), natives already named. Globals get `_Data`-typed names where
   the constant-object table attaches them.
4. **Relink pass**: `_Data.*Impl_` fields ↔ `data.cdb` sheet columns
   (sheet-id join); `ui.*` classes ↔ HBONN prefabs; `battle`/`ent` call
   sites ↔ cdb skill/item rows — feeding `extracted/relinks/`.
5. **Scale estimate**: 2.5M ops is ~minutes of Python per full pass;
   decompiled corpus size ~50–150 MB text. One agent-pass per package,
   `src/` (game code) first — that is where formulas, drop logic and
   unlock conditions live.

Tooling note: crashlink (fetched under `_refs/upstream/` provenance notes)
provides a reference decompiler pipeline for the same format family; we use
it as verifier and shape-reference while keeping our own emitter, so the
pack's outputs stay reproducible from `run_all`-style entrypoints.
