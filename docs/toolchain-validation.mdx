**wtpak.py reads all four Wartales paks fully. It is the primary tool.**

R1's desync diagnosis was correct and is now closed: entry flags bit `2`
means *dataPosition stored as f64* (needed because three of four paks
exceed the 32-bit offset space). With that handled, every pak parses to
an exact tree with zero slack.

Cross-checks:

- **PAKTool** (N3rdL0rd's PakTool v0.2, based on ModTools v1.7.0;
  source `https://github.com/N3rdL0rd/alivecells/releases` tag
  `paktool-v0.3` shipped as `paktool-0.0.3-win-x64.zip`; .NET 9,
  license tag not captured) `expand`s res.pak to exactly 936 files, and
  the PNG is byte-identical (sha256) to wtpak's. Good independent
  verifier; >4 GiB paks untested with it, so it stays the secondary.
- **QuickBMS**: not needed; not tested.

Format census (6-byte peeks, full extension coverage, `_verify/run-log.txt`):

- `.png` in assets.pak is **mostly DDS payloads** (7,769 of 8,447); only
  676 are real PNG. In content.pak the split is 732 PNG / 146 DDS. Trust
  magic, never extension, when routing textures.
- `.fbx` entries are **all HMD models** (Heaps native model format,
  `HMD` magic) — 6,946 in assets.pak. No FBX parsing needed.
- `.prefab` (635 in res.pak) and `.l3d` (303 in content.pak) are HBSON
  (`HBSON\0` magic) — Heaps binary object notation.
- `.envs`, `.envd` = environment/probe data wrapping DDS; `.tx` starts
  `76 2f 31 01 02 02` (68 files, 420 MB — Heaps atlas/format TBD at
  harvest); content `.bin` (10,204 files) = raw float vertex/color/
  splat-style arrays; map `.raw` (2,754) = float coordinate pairs;
  `.dat` (88) start with float pairs too (prefab terrain/model libs).
- No encryption, no compression layer, no crypto gate observed anywhere:
  every sampled payload shows a plaintext known magic at its absolute
  offset, and adler32 is the only integrity mechanism.

## 2. HashLink bytecode verdict

> **Superseded 2026-08-24** by [decompile-dig-1](decompile-dig-1.mdx):
> the types walk completed over all 46,891 types with zero slack and an
> independent cross-check; the "fork kinds ≥19 / observed 22–31+" below
> were desync artifacts of walking from a misaligned offset (the canonical
> debug-files block sits between strings and types). Kept for the record.

**hlbc fails on this build. Plan B (hand parser from engine sources)
is seeded and already delivers the counts.**

- File: `hlboot.dat`, 16,102,040 B, magic `HLB\x04` → HashLink bytecode
  **format version 4**, `flags=0x1` (hasdebug bit set).
- Tool: `hlbc.exe` = hlbc-cli **0.5.0** (Guillaume Anthouard,
  `https://github.com/Gui-Yom/hlbc`, crates.io `hlbc-cli`; MIT).
  Exact failure: `Error: Malformed bytecode (Invalid type kind '22')`.
  Its latest tagged release (gui-v0.3.0) is older than this binary, so
  there is no newer drop to swap in.
- Root cause localized: public HashLink type-kind tables stop at 19–24
  depending on release (checked upstream 1.12/1.13/1.16/master — master
  renumbers the whole enum, so none match); this build emits kinds ≥19
  (observed 22–31+, histogram in `_verify/run-log.txt`). Wartales ships
  a HashLink fork whose type stream hlbc cannot read.

Plan B seed — `pipeline/tools/hlboot_probe.py`, written directly from
the canonical reader semantics (`_refs/`: Reader.hx-equivalent C loader
`hl_code.c` fetched from `HaxeFoundation/hashlink`):

- Header parses cleanly and strictly: nints 1,600 · nfloats 580 ·
  **nstrings 75,321** · ntypes 46,891 · nglobals 34,258 · nnatives 569 ·
  **nfunctions 52,114** · nconstants 27,941 · entrypoint f#52,548
  (> nfunctions — flagged as a fork quirk worth one look later).
- Strings section decodes **75,321/75,321** with strict NUL-separator
  checks, blob fully consumed; contents are unmistakably the real thing
  (`baseShaderList`, `res/assets/worldmap/collides/navmesh.dat`).
- This build has **no top-level debug-files block** despite the flag:
  types begin immediately after the strings blob. ~1,610 debug source
  paths (`hxd/App.hx`…) sit later as a raw NUL-name blob (~0x22E000–
  0x23845C).
- Types walk (classic kind numbering): first 26 types parse cleanly,
  4,220 before drift — blocked only on per-kind payload semantics for
  the novel kinds ≥19. Continuation is mechanical: capture each novel
  kind's payload shape (several behave as single-type-ref wrappers),
  then validate against globals/natives index ranges. No blocker beyond
  iteration; nothing encrypted.

Counts the brief asked for: functions 52,114 · strings 75,321. "Module"
count: HashLink v4 has no module table; nearest proxies are the ~1,610
debug source files and the unique-Haxe-module count derivable from the
46,891 type names once the type walk completes.

## 3. Texture path

Pak texture inventory (by extension × true magic): DDS dominates bytes —
map.pak 24.5 GB of `.dds` tiles (albedo/normal/splat grids), content.pak
4.4 GB DDS + 146 DDS-payload `.png`s, assets.pak 7,769 DDS-payload
`.png`s + 17 `.envs` cubemaps; genuine PNG/JPEG ≈ 1,900 files, mostly UI
scale (res.pak, assets UI dirs).

Conversion plan to webp:

1. Route by magic at extraction time (not by name): `DDS ` → decode
   branch; `\x89PNG` / `\xff\xd8` → direct transcode branch.
2. DDS decode via Microsoft **texconv** (DirectXTex) `-ft tga/png`
   batch (handles BC1/BC3/BC5/BC7 used here), preserving mip-less
   top-level for tile sets; cubemaps (`envs`) decoded face-wise.
3. Transcode everything to webp with `cwebp`/Pillow; catalogue-first
   per doctrine media carve-out — the 31.7 GB map tile set gets a
   MEDIA-CATALOGUE.md row (bytes + counts + derived webp policy) for an
   owner call before bulk conversion.

## 4. Fallback plans A–D (format level)

- **A (primary, validated)**: wtpak.py harvest of all four paks +
  Plan B bytecode dumper (header/counts/strings done; type-walk
  continuation defined in §2). No crypto gate exists to plan around.
- **B (cross-check/rebuild)**: PAKTool expand (proven on res.pak,
  byte-identical) as an independent extractor; CDBTool v1.7.0 (same
  ModTools family) reads/edits CastleDB files if a cdb round-trip ever
  beats direct JSON handling.
- **C (generic)**: QuickBMS Heaps-pak script if a future patch changes
  the container again — the format is small and PAK.txt pins it.
- **D (runtime)**: if static bytecode parsing stalls on the fork's type
  kinds, build the matching HashLink runtime (source tags up to 1.16 +
  fork deltas) and let `libhl.dll`'s own module loader dump structures
  at runtime; last resort is memory inspection of the running client.
  None of these are needed today for the pak layer.
