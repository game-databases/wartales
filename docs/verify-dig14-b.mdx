# Verify Dig 14 B — adversarial audit of the locale wave-2 dig

**Verdict: UNSOUND** — 1 BLOCKER · 3 MAJOR · 4 MINOR.

The dig's *emitted cells* are excellent — every one of 102,088 mechanism-B
overlay cells byte-matches an independently written raw-XML extractor, the
id-joins are provably id-based and semantically right, markup survives
verbatim, stamps are clean, and nearly all headline totals reproduce. The
dig is unsound on **coverage honesty**: a flattener defect silently drops
12,295 translated prose cell-slots from the mechanism-B overlays, an entire
class of ~382 entities whose prose exists in all nine export locales emits
nothing at all (one of them sits inside the round-trip sample and was
misclassified as "drift"), and the UI namespace omits 1,259 keyed strings
sitting in nested groups while reporting "889 per locale" as the inventory.
Two headline proof numbers in the log/PROOF do not reproduce from the
shipped report.

Auditor: fresh Verifier B, no subagents, no commits. Scratch probes:
`output/_verify-dig14b/` (all runnable: `common.py`, `probe1_join.py`,
`probe2_markup.py`, `probe2b_dropped.py`, `probe3_roundtrip.py`,
`probe3b_unaddressed.py`, `probe3c_lostprose.py`, `probe4_filler.py`).
Sources read-only: `extracted/harvest/_lang-bridge/*.xml`,
`extracted/data/_draft/*.jsonl`, `extracted/locales/**`,
`extracted/relinks/*`, `pipeline/tools/locale_bridge_dig.py`,
`output/_dig-locale-wave2/report.json`.

### MAJOR M1 — flatten_struct silently drops repeated tags across sibling `<lineN>` wrappers (12,295 cell-slots)

Anchor: `pipeline/tools/locale_bridge_dig.py::flatten_struct` — the
`if m:` line-branch calls `rec(ch, nc, counters)` passing the **parent's
counters dict through into every sibling line subtree**, so the second and
later occurrences of a tag gain spurious indices (`…[1].text[1]`), miss
their own prose pattern, and are recursed past as "structure". Per-element
fresh counters (what `scan_leaf_map` uses) would have kept them.

Demonstrating probe (their own code):

```python
import locale_bridge_dig as L
fl = L.flatten_struct(ent_G1Sport, raw, L.STRUCT_TEXT_PATTERNS['place'])
# -> ['props.sport.rules[0].desc', 'world.name']
# raw XML has <line1><desc>The other one is on fire...</desc></line1> too
```

`extracted/locales/en/place.json` G1Sport carries exactly those two keys;
the line1 desc exists translated in all locales and is emitted nowhere.

Blast radius (`probe2b_dropped.py`, all 7 kinds × 9 locales):
**12,295 dropped non-empty prose cells**; entities losing ≥1 cell:
element 384, place 3, fiefPlace 1. Top dropped templates:
`props.goals[0].props.helpTips[1].text` ×1098,
`dialog.Start.choices[1].props.customTxt` ×702, `…tipText` ×603 … — note
the vocabulary itself pins `helpTips\[\d+\]\.text`, i.e. the shape was
known and enumerated, yet index≥1 instances fall out. No entity loses ALL
cells (checked), so drift counts are not poisoned and every *emitted*
value stays byte-correct — under-emission only. Their dual-extractor proof
could not see this: it verifies emitted cells against `scan_leaf_map`
(per-element counters) and only where keys agree; the dual-parser ET
proof skipped struct sheets outright.

### BLOCKER B1 — a sample failure resolves everywhere in source and was called a data gap; the class behind it is ~382 entities

`notify/G2TierryAbodeDaugther`, verified end-to-end:

* Draft row: only ref is `title.textKey → notify/title` (leaf absent from
  the export entry in every locale); its real prose sits in
  `props.texts[0].text` with **no textKey** ("Vos questions ont fait
  pleurer Hella." dev-pivot French inline).
* Raw export entries in all 9 locales carry
  `<props.texts><line0><text>` fully translated ("Your questions made
  Hella cry." / "Eure Fragen haben Hella zum Weinen gebracht." …).
* Neither mechanism addresses `props.texts` → entity omitted from all 9
  overlays, counted in `drift_absent_everywhere`, and the log asserts the
  21 failures are "data gaps, not addressing failures".

This is exactly the brief's BLOCKER trigger: a failure that resolves in
some locale = resolver bug. And the sample barely caught it — the class is
large. `probe3c_lostprose.py` (entities whose refs all miss while their
export entries hold non-empty leaves outside every ref'd column):
**382 A-kind entities × 9 locales of unaddressed translated prose** —
notify 311, bonus 35, fiefEvent 28, counter 4, credits 2,
fiefAlignment 1, startChoice 1 (my sweep also flagged confessions 87 —
false positive, excluded: nested `data[].choices[].texts[]` refs cover
those paths; fr/en spot checks confirm e.g. bonus R1FarmSupplyFront
'Supply the Front Lines'/'Approvisionner le front', counter BaseSong
'Adventures Galore'/"D'aventure en aventure" are real lost translations).

Additionally `fiefCondition/GovernmentAssign` fails in fr only, so the log
sentence "**all 21 failures are drift entities failing in every locale**"
is false as stated (it holds for 19/21). That piece is misclassification,
not a resolver bug — fr's fiefCondition sheet genuinely lacks the row
(18 vs en 20 entries) — but the blanket claim does not survive.

## Attack 5 — UI namespace honesty: core claim PASSES, completeness FAILS (MAJOR)

* **The 111-key absence claim is genuine.** All 111 en−fr keys checked
  directly against the master `texts.xml` bytes: 110 have no
  `id="…"`/`_id="…"` hit anywhere; the 111th regex suspect
  (`trait_levels/confirm`) is my own false positive — master's
  `<g id="trait_levels">` holds six **id-less** `<t>` rows. In fact the
  fr parseProblems id-less counts sum to exactly 111
  (unit_ranks 3 + trait_levels 6 + compass 8 + npc_recruit_talk 10 +
  npc_talk_prison 5 + animal_* 8 + bounty_adjectives 62 + comparison 6),
  i.e. the fr vintage usually *has the French text but without ids*, so
  the key is genuinely unaddressable. Claim true as stated; wording could
  note texts-vs-keys (MINOR m4). Totals reproduce: en 889 / fr 778 /
  extra_vs_pivot 0 everywhere; UI dual-extractor 7,890/7,890 reproduces
  from the report.
* ### MAJOR M3 — nested groups dropped from the chrome namespace
  Every locale logs the same 105 `unexpected <g>` problems (battle 3,
  battlemode 17, skills 4, multiplayer 2, tips 16, confirm 3, ui 40,
  npc_recruit_talk_localized 4, title 9, start 7). My token walk over
  `texts_en.xml`: **197 nested `<g>`, holding 1,259 `<t>` leaves**, all
  excluded by `parse_ui` (direct children only). The log sells "40 groups
  + 4 top-level keys; 889 strings per locale" as the group inventory with
  no denominator; `_inventory.parseProblems` lists the raw problem lines
  but nothing quantifies or reconciles the omission, and much of it
  (title/start/confirm/tips) is chrome-shaped. Emit-side-only
  verification again (checks stored strings against the scanner map)
  cannot see drops. If nested groups were deliberately out of chrome
  scope, nothing declares it.
