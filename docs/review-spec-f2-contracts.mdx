## Verdict

**NEEDS_REVISION** — 2 BLOCKER, 5 MAJOR, 6 MINOR.

The load-bearing design is sound: I re-proved the §6 URL bijectivity
independently on 78 real page URLs across 10 kinds without a single
collision, the kind universe is set-equal to `wave_kinds.MANAGED_KINDS`,

## Findings

### BLOCKER-1 — Ground truth frozen at 05:51 was overwritten by dig 14 at 05:58–06:13; §2, §12, the manifest law, and AC4 are false against the disk as found

Anchors: subject §2 table rows "Availability rows", "Locale overlays on
disk"; §12 entire section; §6 `localeCoverage`; AC4 code.

Evidence (all read from disk during this review):

- `extracted/relinks/locale_availability.jsonl` holds **14,456 rows over
  34 kinds**, not §2's "3,779 (item 2,125 · skill 1,373 · class 281)".
  Coverage today: 31 of 40 managed kinds **plus deferred**
  `place` (534) / `group` (790) / `element` (5,078); managed kinds with
  no rows: activity, amb, env, fiefGoal, frescos, loot, recipe, sound,
  unitPattern. File mtime 06:13:36 vs spec mtime 05:51:49.
- Overlays: **317 files** under `extracted/locales/**` spanning those 34
  kinds × 9 locales — not §2's "wave-1 kinds only, today".
- §2's "per-row locale sets bimodal {∅, all 9}" is now trimodal:
  9,472 rows all-9, 4,982 rows ∅, and 2 rows carrying 8 locales
  (fr missing).
- AC4 asserts `len(files) == 27` for `extracted/locales/*/*.json`; the
  same glob returns **317** today → AC4 fails as written.
- AC8 pins `localeCoverage == {mode:"wave-1", kinds:["class","item",
  "skill"]}` and §6/§12 derive per-locale URL existence from it. Post-dig-14
  reality: 31 managed kinds carry overlays, so the pinned value
  misdescribes the plane the manifest exists to describe. §12's own
  framing ("Consequences pinned NOW so dig 14 cannot reshape the
  contracts") is the requirement this landing violates.

PROGRESS.mdx L21 declares "R9 locale wave-2 overlays (dig 14 running)",
so the spec hardcoded pre-regen numbers into a consumed-facts table
while knowing the regen was in flight. Dig 15 (R10 relink matrix
upgrade) is also running and will move the relink row of §2 next. A
contracts spec must either re-freeze these numbers post-dig or cite the
gates instead of restating volatile values; as landed, the review chain
would be passing a document whose acceptance criterion fails on the
machine it targets.

### BLOCKER-2 — §4's identity law states a false observed charset; 754 real entities violate it

Anchor: subject §4 ("Observed charset `[A-Za-z0-9_]`"); propagates to
§5.1 common.schema.json "id pattern", §10 cdnIconPath id segment, and
the markers `entity.id` pattern implied by §9.

Evidence: synthetic ids are `env-0000…env-0086` (87 rows) and
`recipe-0000…recipe-0666` (667 rows) — both contain hyphens; a full
corpus scan flags exactly these two kinds. frescos ids (A1Ruins…) do
conform. So 754 canonical ids fail the charset the spec asserts as
observed. Consequences if the build follows the spec: every pattern
derived from §4 rejects those baseRecords/listEntries; `/data/recipe/
recipe-0000.json` URLs are legal paths whose id segment fails the pinned
pattern; marker rows linking `entity:{kind:"recipe", id:…}` fail the
entityPointer pattern. The stable-id law (localization-architecture §5.1
item 1: the id is verbatim, immutable, the join key) makes "adjust the
ids" unavailable — the contract must describe the real charset.

### MAJOR-1 — AC11 crashes deterministically on the target platform, twice

Anchor: subject AC11 program; §10 pattern text.

Proven by running the embedded program verbatim (read-only):

1. `re.compile` of the §10 pattern fails: `^/cdn/v(?<buildId>[0-9]+)/…`
   uses .NET/ECMA named-group syntax; Python `re` raises
   `error: unknown extension ?<k at position 28`. JSON Schema patterns
   are ECMA-262 where the syntax is legal — but AC11 compiles it with
   Python, so schema-as-specified and AC-as-written are mutually
   inconsistent; one of them must change.
2. Independently of (1), `str(p).replace("\\\\", "/")` normalizes
   double backslashes only; Windows pathlib paths carry single ones, so
   `f.split("output/", 1)[1]` raises IndexError — confirmed on
   `output\cdn\v20318128\class\Admiral.webp`.

The AC cannot reach its first assertion on NE8K. (For the record: after
fixing both mechanics, all 3,779 exported paths match the pattern's
semantics — the underlying claim of §10 is true.)

### MAJOR-2 — Locale-segment spelling conflicts with F4's frozen shell decision; §6 derivation breaks for pt-BR pages

Anchors: subject §4 ("Locale segments … exact strings … `pt-BR`"),
§6 table and namespace list; F4 §2 recorded decision r1 (lowercase
`pt-br` URL segment); PT16 §3 cross-reference to "the pt-BR data-plane
spelling tension between F2 and F4".

F2 pins client-code exact strings for BOTH page and data segments.
F4 (landed) freezes lowercase `pt-br` for page segments while asserting
data-plane URLs keep `pt-BR` "per spec-f2-contracts.mdx §4". Under F2
as landed, the §6 rule applied to a real page `/pt-br/item/X` does not
strip `pt-br` (not in the manifest's prefixed list) and yields
`/data/pt-br/item/X.json` ≠ the pinned `/data/pt-BR/item/X.json` — the
bijectivity I re-proved above holds only for the other seven locales
and the data-side spelling. AC7 cannot catch this: its probe locale is
`sorted(ls)[0]` = `de`. Either F2 adopts presentation ids for the page
leg of the derivation (two-segment-set manifest), or the conflict goes
to the arbiter; silence in F2 while citing F4's bridge is not a state
the URL law can ship in. Recorded in `## conflicts` below.

### MAJOR-3 — AC5's banned-token list does not implement §11's ban list

Anchor: subject §11 banned list vs AC5 `BANNED` array.

§11 bans, but AC5 does not test for: `extracted/` (named explicitly in
§11's harvest/pak-path clause), bare `gate` (only `coordinateGate` and
`publicationPlane` are listed), relink edge bookkeeping `mechanism` /
`valid`, and the registry repo fields `source` / `sourceRef` /
`coordinateRows` that §9 itself strips. A build can pass AC5 while
shipping several vocabularies §11 forbids. Counterweight worth stating
in the spec: some naive additions would false-positive on legitimate
published columns — item has a real canonical column named `tool`
(verified), and `columns`/`enums` are common words — which is presumably
why the list was narrowed; the narrowing just went further than §11's
text allows. Enforcement must match the law or the law must be amended.

### MAJOR-4 — Two spellings of the sole whitelisted provenance carrier

Anchors: subject §11 whitelist (`buildId`, required at every document
root); §9 allowed top-level keys ("buildid crs coordinateTransform
layers regions battleTactical") and projection; AC5(a) requiring
map.published to compose `provenanceEnvelope`.

The registry root key is `buildid` (lowercase, integer — verified on
disk), and §9 keeps it in the published projection, while §11/AC5(a)
require the envelope's camelCase `buildId` at every published document
root. As written, the published map document must carry both spellings
to satisfy §9 and AC5(a) simultaneously, or violate one of them; §2
documents the string-vs-integer asymmetry but not this key asymmetry,
and neither AC detects it. This is exactly the class of seam the spec
elsewhere insists on converting once, explicitly, at the boundary.

### MAJOR-5 — Embedded payload examples contradict the spec's own pinned facts

Anchors: §7 example envelope; §8 example tooltip; AC9 fixtures.

- §7 shows `"count": 1807, "namedCount": 1807` for kind item; the
  canonical corpus has 2,125 item rows, and §2/§6 say 2,125. A consumer
  copying the example writes a fixture that contradicts the contract's
  own coverage semantics (`count` = rows the file holds).
- §7's example row carries `icon: "/cdn/v20318128/icon/Gold.webp"`; item
  Gold exists and its export is `/cdn/v20318128/item/Gold.webp`. No
  `/icon/` directory exists in the export set (verified: only class/,
  item/, skill/, 3,779 files).
- §8's tooltip is for skill `Charge`: no such row exists in
  skill.jsonl (closest real ids: FenrisCharge, ChargedShot) and no such
  webp. Its `availableLocales: ["en","de","fr"]` is impossible under
  the spec's own bimodal availability law (∅ or all 9 — plus the two
  fr-less rows dig 14 just added).
- AC9 fixture `regionId: "Gosenberg"` — real region ids are
  `Gosenberg_1`, `Gosenberg_2` etc. (verified against maps.json); its
  icon path uses the nonexistent `/icon/` segment again.

Examples inside a contracts spec become tests and fixtures (AC6 and AC9
institutionalize exactly that); invented values here are defects, not
illustrations.

### MINOR-1 — AC6 lacks the resolver AC3 deems necessary; threshold arithmetic loose

AC6 validates examples against bare `$defs` subschemas with
`validator_for(s)` and no resolver/store, while AC3 needed a
RefResolver+store for cross-file refs. Any example placed inside
`baseRecord` (which AC5(a) obliges to carry an external `$ref`) makes
AC6 raise unresolvable-ref unless authors confine examples to ref-free
defs — fragile and unstated. Also: the ≥45 threshold sits under the 47
`*.schema.json` files the glob will find (maps.schema.json included,
which has none), silently tolerating two example-less schemas. AC3/AC5's
RefResolver is deprecated in the measured jsonschema 4.26.0 (works
today, warns).

### MINOR-2 — Manifest cannot express the reserved last segment `tooltip`

§6 reserves `tooltip` as a terminal path segment, but api.manifest
carries only first-segment `reservedPrefixes`, and AC7's disjointness
assertion covers first segments only. The machine source of truth is
incomplete relative to the section it serializes.

### MINOR-3 — The shipped CDN export dir is not publish-clean

`output/cdn/v20318128/` contains `misses.jsonl`,
`resolution-proof.jsonl`, `_tool.json` beside the webp trees (verified).
§10 states reason codes "stay in the repo plane"; physically they sit
inside the tree stage 7 will serve. Stage 7 owns the serving set, but
the contracts spec should record that the existing export directory
needs a publish filter, since §10's sentence as written is false of the
directory as found.

### MINOR-4 — AC10 proves totality but not the "dataPlaneOnly imagery absent" clause

The AC strips `publicationPlane` from layers before anything checks
imagery, so a future registry carrying populated non-served imagery
projects cleanly onto map.published while leaking references to
splats/heightmaps (DR-2026-08-18-media-scope). Safe today only because
every non-served layer's imagery happens to be null (verified by dry-
running the projection against maps.json: only world-strategic keeps
imagery). The clause is currently enforced by corpus accident, not by
schema or AC.

### MINOR-5 — §2 consumed-facts table omits textKeyCoverage and hardcodes other volatile numbers

RELATIONS.md's header envelope includes "textKey coverage: 27/27
emitted sheets in the en bridge (35 sheets), drift-absent 0" — part of
the §4.2-as-amended envelope this spec cites — but §2's table omits it.
Combined with BLOCKER-1: restating moving numbers (availability counts,
relink totals ahead of dig 15) in a contracts document guarantees
recurrent staleness; cite the owning gate, freeze only stable shapes.

### MINOR-6 — AC12's porcelain-exactness gate is brittle

`git status --porcelain contracts/ docs/` showing "EXACTLY the ten §14
paths" assumes docs/spec-f2-contracts.mdx is clean (it shows iff dirty)
and that no sibling agent has dirty files under docs/ — the pack runs
concurrent orchestrators on a shared worktree, so the gate flakes for
reasons outside the build piece's control. Scope the assertion to
contracts/ plus an explicit allowlist check instead.
