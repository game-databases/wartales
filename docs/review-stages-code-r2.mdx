## New findings (introduced or widened BY the fixes)

### R12 (NEW, MINOR-latent) — unanchored `relpath` reintroduces finding-A's cwd dependence, crash without report

`validate_all.py:429`: `os.path.relpath(os.path.join(root, fn))` inside
the new recursive walk has no anchor — it resolves relative to **cwd**.
Proof (A4): invoking the validator from any cwd on a different Windows
drive than `--datadir`/`--reldir` crashes
`ValueError: path is on mount 'D:', start on mount 'C:'` — traceback,
exit 1, **no report written**, violating §5.2's record discipline in
exactly R1's shape. This call did not exist before W1 (round 1's scan was
top-level listing) — the R6 rewrite introduced it, and it is the same
cwd-dependence class finding A ruled on. TestFixer hit it this session
(disclosed) and worked around it TEST-side (`cwd=tree["root"]`), leaving
the tool defect in place. In-pipeline unreachable (`Set-Location
$PackRoot`), same-drive isolated invocation fine (A1). Corollary: even
when it doesn't crash, the rendered record paths are cwd-dependent
(A2's `fakeA\extracted\data\place.jsonl` reads differently from another
cwd).

Fix (one line): `os.path.relpath(os.path.join(root, fn), directory)` —
plane-rooted records, no cross-drive failure mode ever. Add a
cross-drive-cwd probe to the validator truth-table while there.

### R13 (NEW, MINOR) — `catalog-parity` mixes planes: matrix from `--reldir`, RELATIONS.md from the tool's own PACK_ROOT

`validate_all.py:354` reads `<tool pack>/extracted/RELATIONS.md`
regardless of `--reldir`, while the matrix side comes from
`args.reldir`. Consistent when the tool lives inside the tree (every
in-pipeline and fakeroot run above), divergent for out-of-tree isolated
validation: a relocated/copied canonical tree is parity-checked against
an UNRELATED rendered file — spurious `catalog-parity=False` (marker can
never match) or, if hashes coincided, false confidence. The F3 extension
deepened reliance on that anchor (it now parses cells out of that file),
and the operational bill already arrived: the suite's md-cell-falsified
leg must snapshot/tamper/restore the SHARED `extracted/RELATIONS.md`
mid-suite — the exact mechanism whose interrupted restore once zeroed
the shared artifact (TestFixer incident, disclosed; now atomic +
read-back-verified, but any concurrent reader during the window still
sees falsified bytes).

Fix (small, either suffices): anchor the MD beside the tree under test
(`<reldir>/../RELATIONS.md`, identical in-pipeline) or take an explicit
`--relations` argument; then rebuild the fault leg on the F15 fakeroot
lever — copy the tools + tampered MD into tmp and PACK_ROOT resolves
inside the fakeroot, deleting the shared-file window entirely.

### R14 (RESIDUE, partly pre-existing; MINOR-latent) — validator's own parsing is unguarded: corrupt input loses the whole report

The child verifier guards its parses (fail records); the parent does
not: `load_jsonl` meta (:157), per-edge `json.loads` (:266), availability
rows `json.loads` + direct field indexing (:305–311), matrix load
(:347) all raise on malformed bytes → traceback, no report, discarding
checks ALREADY recorded (e.g. a corrupted pair file flips
`verifier-gates=False` in `gates` and then crashes before the envelope
write). Pre-existing for the pair/meta/matrix loads; the F4 rewrite kept
the direct `row["availableLocales"]` indexing. All T10 faults are valid
JSON, so the class is untested. Directive: wrap each per-row/per-file
parse and route the fault into the owning check's record (the check then
fails loudly with the offending locator — never a lost report).
